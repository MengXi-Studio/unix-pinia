# @meng-xi/unix-pinia v0.2.2 发布：Kotlin 编译修复（StorageAdapter 可空函数字段裸调用）

> v0.2.2 为**修复版本**：修复 v0.2.1 引入的安卓 Kotlin 编译失败——`StorageAdapter` 三个可空回调字段在 `getStorageRaw` / `setStorageRaw` / `removeStorageRaw` 内被裸调用，Kotlin 端生成 `Function1<...>?` 的非空调用而报错。纯实现层修复，**API 零变化**，升级无任何代码改动。

## 一、现象与根因

**现象**：v0.2.1 在 HBuilderX 运行 / 云打包到安卓（Kotlin 编译链）时，编译插件 uni_modules/ux-pinia 直接失败：

```
error: Reference has a nullable type 'Function1<@ParameterName(...) String, Unit>?'.
Use explicit '?.invoke' to make a function-like call instead.
  at uni_modules/ux-pinia/utssdk/persist/storage.uts
```

**根因**：v0.2.1 为桥接安全将 `StorageAdapter` 的三个回调字段（`get` / `set` / `remove`）声明为可空函数类型（`((key: string) => string | null) | null` 等，null 字段回退默认 uni storage 行为）。可空声明使 `setStorageAdapterImpl` 内的合并逻辑获得了判空保护，但存储原语的三个出口函数仍对 `adapter.get` / `adapter.set` / `adapter.remove` 直接裸调用——Kotlin 端字段类型为 `Function1<...>?`，非空调用编译报错。

**影响范围**：仅安卓（Kotlin 编译链）受影响，Web 纯 JS 无此约束；使用默认 uni storage 或自定义适配器的代码均触发（实现层内部路径，与调用方式无关）。

## 二、修复方式

三个出口函数统一改为「本地 val 中转判空后回退默认实现」——与 `setStorageAdapterImpl` 已验证的同款模式（Kotlin 不对字段 smart cast，必须先落到本地变量再调用）：

```uts
export function removeStorageRaw(key: string): void {
	// 字段为可空函数类型：本地 val 中转判空（Kotlin 不对字段 smart cast，裸调用报 Function1? 错误）
	const removeFn = adapter.remove
	const fn = removeFn != null ? removeFn : defaultRemove
	fn(key)
}
```

`getStorageRaw` / `setStorageRaw` 同款处理。判空的 else 分支回退默认 uni storage 实现，与 `setStorageAdapterImpl` 的合并语义一致——运行时行为不变（`adapter` 初始化与替换均已补齐默认实现，回退分支不实际触发）。

## 三、升级指南（0.2.1 → 0.2.2）

仅需更新依赖，代码零改动：

```bash
pnpm add @meng-xi/unix-pinia@0.2.2
```

（或插件市场重新导入 ux-pinia。）

- `StorageAdapter` 类型声明、`setStorageAdapter` / `setStorageAdapterImpl` / `clearPersistedState` 等 API 签名不变
- store 定义、`$`-API、持久化双钩子契约、`pinia.usePersistPlugin(options)` 登记形态均不变
- v0.2.0 → v0.2.1 的升级指引继续适用：基座场景持久化登记统一走 `usePersistPlugin(options)`
